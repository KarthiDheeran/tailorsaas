**Edit Order flow (chunk 7) shipped 2026-07-05**, enabling the Order Details drawer's Edit Order button (previously disabled/"Coming soon" — see chunk 6 above). Clicking it opens `components/orders/edit-order-drawer.tsx`, a new right-side drawer (`w-full sm:w-[560px] md:w-[680px]` — wider than the read-only details drawer since it holds an editable items table) pre-filled from the selected order and its customer. It's a dedicated component rather than New Order's `OrderForm` reused with a `mode="create"|"edit"` prop: the two forms' field sets diverge too much to share cleanly (Edit Order surfaces Customer Name/Phone/Address/Area and Order Status, which `OrderForm` has no notion of; it omits Trial Date/Advance Paid/Payment Mode, which `OrderForm` requires) so a focused new component was lower-risk than retrofitting, per the user's own fallback instruction. Closing via the X button or backdrop click prompts `window.confirm("Discard unsaved changes?")` if any field differs from its initial snapshot; the explicit Cancel button discards without prompting, since clicking something labeled "Cancel" is already the confirmation. On save, `app/orders/page.tsx` closes the edit drawer, reopens the Order Details drawer on the freshly updated order, and bumps the same `refreshTick` state the inline status editor already uses so the table reflects the change — no page-wide reset of filters/search/pagination. One layout bug was caught and fixed during verification (Playwright-driven, screenshotted): the items grid's `1fr` columns used CSS Grid's default `min-width: auto`, which sizes a track to its content's min-content rather than letting it shrink, so number inputs overflowed the card at this drawer's narrower width; fixed with `min-w-0`/`w-full` on the grid cells (a bug specific to this narrower drawer — `OrderForm`'s original copy of this grid doesn't hit it, since it renders full-width on the New Order page).

**Edit Order's Measurement action shipped the same day**, adding a per-item "Measurement" button (Ruler icon, next to Remove — the item row grid grew to `[2fr_1fr_1fr_1fr_auto_auto]` and the drawer widened to `md:w-[760px]` to fit it) that opens `components/orders/garment-measurement-modal.tsx`'s `GarmentMeasurementModal`, a centered modal (`z-[60]`/`z-[70]`, above the edit drawer's own `z-50`) for that item's garment type. This is a direct, explicitly-requested reversal of the Customers module's "no per-garment-type measurement records" line — see the "Reversal note" under the Customers module spec's Measurements section below for why it was built anyway and what's still out of scope. New type `GarmentMeasurement` (`lib/types.ts`) and stub-data accessors `getGarmentMeasurement`/`getGarmentMeasurementsForCustomer`/`saveGarmentMeasurement` (keyed by `customerId` + a lowercased/trimmed `garmentType`, overwrite-in-place, no history). The modal originally rendered 13 fixed common fields regardless of garment type; as of the New Order flow rework below, it takes a `fields` prop and renders the garment-specific field set from `lib/garment-catalog.ts`'s `getMeasurementFields(garmentType)` instead (falling back to a small generic set for free-text `particular` values that don't match a known garment type) — see below. Fields (garment-specific or fallback) plus Fit Notes and Notes are all optional/blank-allowed, stored as a flexible `Record<string, string>` rather than named fields (same rationale as `MeasurementProfile`'s existing fields, but deliberately not merged with it — different shape, different key). Crucially, **measurement edits don't touch stub-data when "Save Measurement" is clicked** — they're held in `EditOrderDrawer`'s own `measurementsByGarment` state (keyed by garment type) and only actually persisted (one `saveGarmentMeasurement` call per touched garment) inside the order's own `handleSubmit`, alongside `updateCustomer`/`updateOrder`; this is what makes the order-level Cancel/discard-on-close behavior correctly discard measurement edits too, and why `isDirty` now also diffs `measurementsByGarment` against each garment's persisted record. A compact **Measurements** summary card (below Items, above Payment Summary; only rendered when the order has at least one item with a non-blank particular) lists each distinct garment type from the current item rows with a computed "N fields saved" count (`countFilledFields` — non-blank entries across `values`/`fitNotes`/`notes`, not tied to a fixed denominator) and either "updated `<date>`" (persisted) or "unsaved changes" (touched this session but not yet order-saved) or "No measurements saved yet". No separate Measurements nav tab was added, per the instruction — this is reachable only from Edit Order's item rows.

**New Order flow reworked around a garment catalog (chunk 8) shipped 2026-07-05**, replacing the generic gender-driven Male/Female measurement step that used to sit between customer selection and the order form — real tailoring software drives measurements/pricing off the garment being ordered, not a one-size-fits-all body profile collected up front. The flow is now: search-or-create customer → **straight to the order form** (no measurements step) → per-item Garment Type/Size/Add-ons/Measurements/Rate on the order itself. `app/orders/new/page.tsx`'s step machine dropped `"measurements"` entirely (now just `"search" | "new-customer" | "order"`); `NewCustomerForm`'s submit button at this call site changed from "Continue to Measurements" to "Create Customer & Continue" (passed explicitly as `submitLabel`, the two other call sites — Customers module Add/Edit — already pass their own explicit labels so were unaffected). New `lib/garment-catalog.ts` is the config/helper module named in this chunk's brief: `GARMENT_TYPES` (Shirt/Pant/Blouse/Suit/Kurta/Sherwani/Petticoat/Alteration/Custom), `SIZE_OPTIONS` (XS/S/M/L/XL/XXL/Custom), and per garment type a `measurementFields` list, `pricing` (`Partial<Record<SizeOption, number>>`), and `addOns` list, plus helpers `getMeasurementFields`/`getDefaultRate`/`getAvailableAddOns`/`computeAddOnsAmount`. Pricing + add-ons tables were only specified for Shirt/Pant/Blouse (per the brief's examples) — the other five garment types have empty pricing/add-ons (rate is always manual, no add-on picker shown) until a real catalog is speced; Sherwani/Petticoat were also given assumed measurement-field lists (no explicit spec), and Alteration/Custom intentionally have no fixed measurement fields (Fit Notes/Notes only), per the brief's own fallback for Custom. `components/orders/order-form.tsx` was rewritten: item rows are now Garment Type (dropdown, required) | Size | Qty | Rate | Add-ons | Amount | Measurements | Delete, replacing the old free-text Particular/Qty/Rate/Amount row. Rate auto-fills from `getDefaultRate(garmentType, size)` on either changing; a direct edit to Rate sets a per-row `rateOverridden` flag that makes future garment/size changes stop overwriting it (manual override always wins for that row, per the brief). Add-ons are a small checkbox popover (`AddOnsPicker`, local to `order-form.tsx`, styled like `OrderStatusEditor`'s popup) whose selected amounts fold into the item's `amount` alongside `qty * rate`. `OrderItem` (`lib/types.ts`) gained optional `size` and `addOns?: OrderItemAddOn[]`; `particular` is kept as-is (still the garment type's label) so existing display code (`orders-table.tsx`'s items summary, `order-details-drawer.tsx`) didn't need to change. Each item row has an "Add Measurements"/"Edit Measurements" button (label depends on whether any field already has data) opening the same `GarmentMeasurementModal` from the Edit Order chunk above, now with `fields={getMeasurementFields(garmentType)}` so it only shows that garment's fields (e.g. selecting Blouse never shows Chest, selecting Pant never shows Bust). New customer-level type `CustomerMeasurements` (`lib/types.ts`) — distinct from both gender-driven `MeasurementProfile` (untouched, still owns the Customers module's measurements section) and per-garment `GarmentMeasurement` — is a flexible `Record<string, string>` baseline keyed only by `customerId`, seeded in `stub-data.ts` for the 4 sample customers (converted from their existing `MeasurementProfile` data, an assumption made to give auto-fill something to demonstrate — a customer created from scratch starts with none). Opening an item's Measurements modal seeds it from `getGarmentMeasurementDraftSeed(customerId, garmentType)`: the customer's baseline values, overridden per-key by that customer+garmentType's previously-saved `GarmentMeasurement` if one exists (so a customer's general Bust auto-fills a new Blouse order, but a garment type they've ordered before uses its own last-saved values first). On Save Order, each touched item's measurement draft is persisted via the existing `saveGarmentMeasurement` (per garment type) **and** merged into the customer's `CustomerMeasurements` baseline via new `saveCustomerMeasurements` (upsert-merge by key, so different garments' orders each contribute to the same baseline without clobbering fields the other garment types don't touch) — filtered through `pickBodyMeasurements` so only the canonical body-measurement keys (Bust/Chest/Waist/Hip/Shoulder/Sleeve Length/Armhole/Neck/Blouse Length/Shirt Length/Kurta Length/Pant Length/Inseam/Thigh/Bottom/Rise/Cuff) get written back, not garment-specific-only fields like Neck Depth or Coat Length. **Minor Edit Order alignment** (per this chunk's own instruction to update it carefully rather than leave it broken): its `DraftItem`/`toDraftItems` now carry `size`/`addOns` through untouched (no dropdown/picker UI added there — `particular` stays free text), its item-row Amount display and `computedItems` now include `addOns` amounts (previously only `qty * rate`, which would have silently dropped add-on charges on any edit), and its Measurement button now passes `fields={getMeasurementFields(it.particular)}` too. **Not built, per the brief's explicit exclusions**: no standalone Customers-tab measurements editor for the new `CustomerMeasurements` baseline (it's only read/written through New Order's per-item modals), no Garment Type/Size/Add-ons editing UI added to Edit Order itself, no catalog admin UI, no Customer `notes` field (listed as "if already supported" in the brief — it isn't, so it was left out rather than extending the Customer type as a side effect), no changes to Order Details drawer's items table (still shows Particular/Qty/Rate/Amount only — size/add-ons aren't broken out there, just folded into the existing Amount).

**Supabase backend migration (Phases 1–8) shipped 2026-07-08 through 2026-07-10**, closing the gap the line above used to describe. This wasn't one chunk but a sequence: **Phase 1–2 (auth foundation)** added real Supabase Auth — `supabase.auth.signInWithPassword`/`resetPasswordForEmail`/`updateUser` power `app/(auth)/login|forgot-password|reset-password|change-password`, gated by `middleware.ts` (redirects unauthenticated requests to `/login`, and forces a `/change-password` visit when a `profiles.must_change_password` flag is set — e.g. for newly-created users). `lib/supabase/{client,server,admin,middleware}.ts` are the four Supabase client constructors (browser/anon, server/anon+cookies, service-role/admin, and the middleware session helper); `lib/auth/require-server-permission.ts`'s `requireServerPermission`/`getServerCallerPermissions` is the mandatory server-side permission check every Server Action calls first, since (per its own comment) a client-side check is "never a security boundary." **Phase 3–4 (roles/permissions/users go real)** replaced the entire "Frontend-only role/permission simulation" stack described further down: `lib/mock-users.ts` is deleted outright, `lib/roles.ts` now reads/writes a real `roles` table (`supabase/migrations/0001_auth_foundation.sql`) with the Admin role's permissions pinned server-side (both an RLS policy and a code-level guard in `updateRole` block weakening it), and `lib/profiles.ts` is the real replacement for the old mock-user list, reading a `profiles` table keyed to `auth.users`. `components/auth/current-user-provider.tsx`'s `CurrentUserProvider` now resolves the logged-in user's actual session + `profiles` row + `roles.permissions` on every load/auth-state-change instead of switching between three hardcoded mock identities — **the Users & Access popover-switcher UI described below no longer exists**; who you are is now who you logged in as. `RequirePermission`/`AccessDenied`/every module's permission-gating call sites (Orders' `getAvailableOrderStatuses`, Customers' measurement-editing gates, Catalog's `canManage`, Staff's `staff.manage`, Reports' `visibleTabs`, etc.) are unchanged in behavior — they still just read `hasPermission`/`effectivePermissions` off the same context, which never cared whether a permission came from a mock user or a real one. **Phase 6 (business data)** migrated `lib/data/stub-data.ts` out of existence in four sub-chunks, each adding a migration + rewriting one `lib/*.ts` selector file's backing store while preserving its exported function names: 6A Customers (`0004_customers.sql` — `customers`, `customer_measurements`, `garment_measurements` tables), 6B Catalog (`0005_catalog.sql`), 6C Orders (`0006_orders.sql` — `orders`+`order_items`, with `createOrder`/`updateOrder` now calling transactional Postgres RPCs `create_order_with_items`/`update_order_with_items` instead of raw array mutation), 6D Staff (`0007_staff.sql` — `work_assignments`+`staff_payments`, the previously-empty stub arrays now real and RLS-governed). Every `lib/data/*-db.ts` file's functions take a `SupabaseClient` as their first parameter and return a `Promise`; they're called from `"use server"` Server Actions (one `actions.ts` per module route, e.g. `app/(shell)/orders/actions.ts`) that call `requireServerPermission` before touching data, not directly from client components anymore. **Phase 8 (2026-07-10)** is documented in its own entry below (Payments/Job Cards/Inventory/Expenses). Routes also moved during this window: every module page now lives under `app/(shell)/**` behind a shared `AppShell` (auth-aware loading state, sidebar), not the old flat `app/orders`, `app/customers`, etc. — only the print routes (`app/orders/[id]/print/**`) stay outside the shell group, unchanged, since they still need zero app chrome. See the note at the top of the "## Architecture" section below for the accurate current shape; the per-module Architecture bullets past that note are still correct about UI/component behavior but describe the old flat routes and `stub-data.ts` for where data comes from — read `lib/data/*-db.ts` wherever they say `stub-data.ts`.

**Payments, Job Cards, Inventory, Production, and Settings modules shipped 2026-07-10 (Phase 8),** built without a documented brainstorm-and-confirm conversation in this file (same gap the Staff module note below flags for itself — treat the detail here as the working baseline, not a re-litigated spec). All five landed in one commit on top of the Phase 6 data migration above.

- **Payments is a direct, deliberate reversal of the Orders/Customers specs' "no multi-installment support, no Add Payment action, no payment ledger" rule** (repeated in three places below: Orders' Payments section, Orders' "Explicitly out of scope," and Customers' Payment Summary section). `supabase/migrations/0008_payments.sql` adds a real `payments` ledger table (`order_id`, `amount`, `payment_date`, `payment_mode`, a server-computed `payment_type` of `Advance/Partial/Final`, `voided`/`voided_at`/`voided_by`/`void_reason` — **soft-delete only, no hard delete path exists anywhere**, per the migration's own comment). `orders.advance_paid`/`balance`/`payment_status` are no longer a one-time snapshot write — a trigger recomputes them from the sum of that order's non-voided payments on every insert/void. All writes go through two `security definer` RPCs with their own server-side permission checks: `record_payment` (new `orders.recordPayment` permission; validates amount > 0, date not in the future, amount ≤ current balance — no overpayment) and `void_payment` (new `orders.voidPayment` permission, requires a typed reason). `lib/data/payments-db.ts` (`getPaymentsForOrder`, `getAllPayments`, `recordPayment`, `voidPayment`) and `app/(shell)/orders/actions.ts`'s `recordPaymentAction`/`voidPaymentAction` are thin wrappers with zero mutation logic of their own — validation lives entirely in the SQL RPCs. The result is genuinely unbounded partial payments per order (not the old two-step advance/balance-at-delivery model): `components/orders/order-details-drawer.tsx` now has a "Record Payment" button (gated `orders.recordPayment`, opens `record-payment-modal.tsx`) and a Payment History list (`payment-history-list.tsx`, gated `orders.viewPayments`, with an inline Void action gated `orders.voidPayment`) — this is exactly the quick action chunk 6's Project status entry above said was deliberately not built; it has now been built, superseding that call. A standalone `/payments` page (gated `anyOf: ["orders.viewPayments", "expenses.view"]`) is a three-tab **operational** screen — Collections (ledger view), Pending Dues (every order with balance > 0), and Expenses (a separate, unrelated new module off `0010_expenses.sql`/`lib/data/expenses-db.ts`) — explicitly scoped narrower than Reports' analytical Payments tab (today/this-week-style presets only, no Export/Print, no Outstanding/Overdue analytical cards) per its own code comment; actual recording/voiding still only happens from the Order Details drawer, this page is read-only + Expenses CRUD. Two new permission groups were added beyond the old 23-key set: **Accounts** (`expenses.view`/`expenses.manage`) and **Inventory** (`inventory.view`/`inventory.manage`), alongside three new Orders-group keys (`orders.viewPayments`/`orders.recordPayment`/`orders.voidPayment`, a three-level dependency chain). Reports' Payments tab (see Reports spec below) still reads its own selector rather than the new ledger table directly as of this writeup — **not yet reconciled**, worth double-checking before trusting Reports' payment figures against the new ledger.
- **Job Cards is a new, separate workshop-tracking entity — one row per garment unit, not per order or per order line.** `supabase/migrations/0009_job_cards.sql`'s `sync_job_cards_for_order()` generates one `job_cards` row per unit of `order_items.qty` (soft-cancelling surplus rows if an order is edited down), each with its own `current_stage` (`Unassigned/Cutting/Stitching/Embroidery/Finishing/Trial/Alteration/Ready/Delivered/Cancelled/Delayed`), `assigned_staff_id`, `priority`, `due_date`, and jsonb `customer_snapshot`/`measurements_snapshot`. `app/(shell)/orders/actions.ts` calls `syncJobCardsForOrderAction` on order create/edit to keep this in sync. `lib/job-cards.ts`'s `buildJobCards()` is a pure client-safe fallback that synthesizes ephemeral (non-persisted) job cards from `orders`+Staff `WorkAssignment` records when the migration hasn't been applied yet (`isMissingJobCardsSchemaError` detects this and degrades gracefully with a banner) — `lib/data/job-cards-db.ts` is the real persisted layer (`getJobCards`, `assignJobCard`, `startJobCard`, `completeJobCard`). The standalone `/job-cards` page (gated `anyOf: ["orders.view", "staff.view"]`) is a filterable queue (Active/All/Unassigned/Delayed/Ready/Delivered/Cancelled) with an "Assign Work" drawer action gated `staff.manage`. **This is a separate concept from the existing `orders/[id]/print/job-card` print route** — that route still prints one worksheet per whole order from `getOrderByIdAction`/`getGarmentMeasurementAction` directly and has not been rewired to read the new per-unit `job_cards` table.

## Orders module — finalized spec

This is the first module being built. Customers and Measurements are covered here because they're tightly coupled to Orders.

### Customer
- Customer Number (auto)
- Name, Phone Number, Address, Area/Locality
- Gender (Male / Female) — determines which measurement fields are shown

### Measurement profile (per customer)
- One profile per customer, manually editable/overwritable. **No history/versioning** — updating overwrites in place and applies to all future orders.
- **Superseded 2026-07-05** (see the Customers module's Measurements section below for the full rationale): the original gender-driven Male/Female field split described here (`MeasurementProfile`/`MaleMeasurements`/`FemaleMeasurements`) was deleted — it was a second, disconnected measurement store that caused a real bug (New Order's measurements never showed up on the Customers profile page). The Customers module's profile/edit-measurements pages now read/write `CustomerMeasurements` instead — the same flexible, canonical body-measurement baseline New Order's per-item modals already used — grouped into Upper Body / Lower Body / Garment Length / Style / Notes (not gender). Gender stays on `Customer` itself (still shown on the profile header, still asked on Add/Edit Customer) — it just no longer determines which measurement fields are shown.
- **Coexists with one other measurement store** (see chunk 8 in Project status above for the full rationale): `GarmentMeasurement` (per customer + garment type, from the Edit Order/New Order Measurement action) — a separate, garment-scoped record, not merged into the customer-level baseline wholesale (only its canonical body-measurement keys get merged back, per `pickBodyMeasurements`).

### Order
- Order Number: auto-generated, format `ORD-2026-0001`, resets yearly
- Order Date, Trial Date, Delivery Date
- Order Items table (one row per garment): Serial No, Particular (Shirt/Pant/Suit/Blouse/etc.), Qty, Rate, Amount. As of chunk 8 (2026-07-05, New Order only — see Project status above) each row was Garment Type (dropdown, not free text) / Size / Qty / Rate / Add-ons / Amount / a Measurements button; as of the later "New Order wired to Catalog" chunk the same day, the dropdown, Rate auto-fill, Add-ons, and Measurements field set are all driven from the **Catalog module** (`lib/catalog.ts`'s active garment types/base price/linked add-ons/linked measurement fields), not the old static `lib/garment-catalog.ts` templates — Rate auto-fills from Catalog's base price (manually overridable, override persists across further garment changes), Add-ons only lists that garment's linked master add-ons, and Amount = Qty × (Rate + selected add-ons total). As of the "New Order Catalog integration refined" chunk, Size was dropped from the row entirely (tailoring orders here are measurement-driven, not size-driven) — the row is now Garment Type / Qty / Rate / Add-ons / Amount / Measurements. Edit Order still shows Particular as free text (not yet upgraded to the dropdown), but carries `size`/`addOns` through untouched (New Order simply never sets `size` anymore) so editing an order created via New Order doesn't lose that data.
- Total Amount: auto-summed from item rows
- Order Status (added 2026-07-05, simplified to 5 values the same day — see note below): `In Progress | Ready | Delayed | Delivered | Cancelled`, a real manual field on `Order` (`lib/types.ts`'s `OrderStatus`), defaults to `In Progress` on `createOrder`. The original build shipped 7 values (`Pending`/`Trial Ready` included); both were dropped as MVP scope-reduction — too many stages would confuse shopkeepers, and finer production-stage tracking (Cutting/Stitching/Embroidery/etc.) is explicitly deferred to a future Production module, not folded into this field. Editable inline via a dropdown on the status chip in `OrdersTable` (`components/orders/orders-table.tsx`'s `OrderStatusEditor`, calling `updateOrderStatus(id, status)` in `lib/data/stub-data.ts`) — this is the primary way it's set for now; a New Order/Edit Order form field is deferred. Editing is opt-in per `OrdersTable` usage via its `editableStatus`/`onStatusChange` props: **on** for the Orders page's two views (all-orders and selected-customer), **off** (read-only chip) for the Customers profile page's order history and the Reports Orders tab, since Reports is explicitly read-only/no-new-mutations. Status filter dropdown lives in the Orders page's filter row (`components/orders/order-list-filters.tsx`), alongside Payment and Delivery filters.
- Previous Orders panel: shows the linked customer's past orders (Order No, Date, Garments, Qty) for quick reference

### Payments
- Order Total (from items), Advance Paid, Balance (auto = Total − Advance, paid at delivery)
- ~~Only two payment steps: **advance + balance at delivery** — no multi-installment support~~ **Reversed 2026-07-10 — see the "Payments, Job Cards, Inventory, Production, and Settings modules" entry in Project status above.** A real payment ledger (`payments` table) now backs `Order`, and an order can accumulate any number of Advance/Partial/Final payments via the Order Details drawer's "Record Payment" action. `advance_paid`/`balance` are now trigger-derived from the ledger, not a one-time write.
- Payment Mode is a manual field (Cash, GPay, UPI, Card, Bank Transfer, Cheque, etc.) — **no payment gateway integration**, the SaaS just records how payment was taken

### Unified search / entry flow
A single search (by phone number or customer name, both with autosuggest) drives everything — there is no separate "search" screen vs "new order" screen:
- **Match found** → shows customer details + full order history table (latest first). From there the shopkeeper can open an existing order to view details, or start a New Order for that customer (pre-filled with saved details/measurements).
- **No match found** → treated as a brand new customer: create customer → gender-driven measurement profile → new order.

### Explicitly out of scope for now
- Reminder system (trial/delivery/payment reminders)
- ~~Multi-installment payments~~ **Reversed 2026-07-10 — see the Payments section above.**
- Any "Book" column/reference
- Payment gateway integration

**Reversal note (2026-07-05):** the Order Status field above was previously listed here as out of scope ("dates are enough for v1"), and had been reaffirmed twice more — Dashboard dropped a "Production Queue" section and Reports dropped "Production Reports" for the same reason. The user asked for it directly (with a concrete mockup showing the column/chips/filter), so it's now built as a real field — see the Order section above. ### Measurements
- **Rearchitected 2026-07-05 (persistence-bug fix):** the gender-driven `MeasurementProfile`/`MaleMeasurements`/`FemaleMeasurements` types this section used to describe are gone — deleted from `lib/types.ts` along with `measurementProfiles`/`getMeasurementProfile`/`saveMeasurementProfile` in `lib/data/stub-data.ts` and `components/orders/measurement-form.tsx`. - **Architecture rule now in force:** Customer Profile Measurements (`CustomerMeasurements`) = latest reusable body values, overwrite-in-place, no history. `GarmentMeasurement` (per garment type, from Edit Order/New Order's per-item modal) = a separate, garment-scoped record — not a frozen per-order snapshot (still keyed by customerId + garmentType only, no per-order-instance history; that's an existing, unchanged convention, not something this fix introduced).
- The Customers profile card (`components/customers/measurements-card.tsx`) and Edit Measurements page (`app/customers/[id]/measurements`, via new `components/customers/customer-measurements-form.tsx`) both render/edit `CustomerMeasurements.values` grouped into **Upper Body / Lower Body / Garment Length / Style / Notes** — the exact same grouping already used by the Catalog module's "Required Measurements" checklist, now hoisted to a shared export, `MEASUREMENT_FIELD_GROUPS` + `measurementFieldLabel`, in `lib/catalog.ts` (both `components/catalog/garment-type-drawer.tsx` and the Customers components import it, rather than each keeping its own copy). - `lib/garment-catalog.ts`'s `pickBodyMeasurements` (which filters an order item's entered measurement values down to the customer-baseline-eligible keys before `saveCustomerMeasurements` merges them in) had two bugs fixed alongside this: (1) its canonical key set was missing `neckDepthFront`/`neckDepthBack`/`knee`, so a Blouse's Neck Depth fields — despite being real fields on that garment and part of the new grouped profile display — were silently dropped instead of merging back; the canonical set is now derived directly from `MEASUREMENT_FIELD_GROUPS` (excluding the Notes group) so it can never drift from what the profile page displays. (2) It didn't filter blank values, so an untouched/cleared field in an order's measurement popup (whose draft is seeded from the customer's existing baseline, extended with a garment's own fields) could silently overwrite an already-saved non-blank value on the customer profile with an empty string; it now drops blank entries so the merge is genuinely "entered values only," never a blind overwrite of the whole object.
- Editing happens either inline per-item in the New Order/Edit Order flow (merges only that item's entered fields into the baseline, last-entered-value-wins across multiple items in the same order), or standalone via the profile page's "Edit Measurements" link (a full-form save of whatever's currently in the form, same as any normal edit page — not merge-only, since the whole grouped form is visible and editable there).
- **Reversal note (2026-07-05):** a second, per-garment-type measurement model (`GarmentMeasurement` in `lib/types.ts` — customerId + garmentType + flexible key-value `values` + `fitNotes` + `notes` + `updatedAt`) was added as part of the Edit Order flow's Measurement action (see "Edit Order flow (chunk 7)" in Project status above), directly reversing the "Per-garment-type measurement records... reverses 'no history/versioning'" line this section used to carry unconditionally. It's scoped narrowly, same overwrite-in-place convention (no version history per garment type — editing replaces the prior save for that customer+garmentType). It still does **not** reopen: version history/comparison, "Measured By", reference images, printing, or body diagrams — those remain out of scope below. There is still no dedicated Measurements nav tab; this lives only inside Edit Order/New Order (and reads/writes the same customer-scoped data the Customers-tab UI also uses).

- ~~**No "Add Payment" action or payment ledger** — recording a standalone payment against an existing order would reverse the Orders spec's "no multi-installment support" rule~~ **The underlying rule this protected was reversed 2026-07-10 — a real payment ledger now exists (see Orders' Payments section above), and Order Details has a Record Payment action.** Not independently verified whether the Customer Profile page itself gained its own Add Payment entry point as part of that chunk (the reversal was researched at the Orders/Payments-module level) — check `components/customers/payment-summary-card.tsx` before assuming either way.

## Catalog module — finalized spec (MVP)

The shopkeeper-facing setup/rules layer for garments: base price, required measurement fields, and add-ons/extras per garment type. **Concept boundary, load-bearing for how this module is scoped:** Catalog = garment setup/rules; it is not where a customer's actual body measurement values live (that's `Customer`/`GarmentMeasurement`/`CustomerMeasurements`), and it is not an order transaction (that's `Order`). See the "Catalog module (MVP)" and "Add-ons/Extras became a reusable master" notes in "Project status" above for what shipped, the file/type-naming collision avoided with `lib/garment-catalog.ts`, and what's deferred.

Catalog has two tabs: **Garment Types** and **Add-ons / Extras**.

### Add-ons / Extras master
Reusable extras, defined once and linked into any number of garment types by id — not redefined per garment (avoids duplicate entries like "Inner Pocket" repeated under Pant, Shirt, Coat, etc.). Each has: Add-on Name, Default Price, Status (Active/Inactive). Table: Add-on Name, Default Price, Status, Actions (Edit, Deactivate/Activate — no delete). Add/Edit is a small drawer (Name, Default Price, Status). Deactivating an add-on removes it from other garment types' *selectable* checklist but does not strip it from a garment's existing `addOnIds` — no silent data loss.

### Garment Type
- Garment Name, Base Price, Status (Active/Inactive) — the three Basic Details fields
- Required Measurements: a checklist of which fields (from the fixed global library, grouped into Upper Body / Lower Body / Garment Length / Style / Notes) this garment needs measured
- Add-ons / Extras: a checkbox list of which *master* add-ons apply to this garment (no free-typed name/price here — pick from the master defined in the other tab)

### Global measurement field library (fixed, `lib/catalog.ts`'s `measurementFields`)
Chest, Bust, Waist, Hip, Shoulder, Sleeve Length, Armhole, Neck, Shirt Length, Blouse Length, Kurta Length, Pant Length, Inseam, Thigh, Knee, Bottom, Rise, Cuff, Neck Depth Front, Neck Depth Back, Fit Notes, Notes.

### Catalog List (Garment Types tab)
- Table columns: Garment Type, Base Price, Measurement Fields (shown as a count, e.g. "6 fields", not the full list), Add-ons (count of linked master add-ons, e.g. "3 add-ons"), Status, Actions
- Row actions: Edit, Deactivate/Activate — no delete. Deactivating hides a garment type from `getActiveGarmentTypes()` (what New Order would consume once wired up) but keeps it in the Catalog list/data.

### Add/Edit Garment Type
- Opens a right-side drawer (shared component for both modes)
- Validation: Garment Name and Base Price required, Base Price ≥ 0; at least one measurement field is recommended but not enforced, and that nudge doesn't show at all for garments named Alteration/Custom
- Calculation this data feeds (for New Order, once wired up): Item Amount = Qty × (Base Price + sum of selected add-ons' Default Price) — implemented today as `calculateGarmentAmount` in `lib/catalog.ts`, not yet called from anywhere

### Explicitly out of scope for this chunk
- New Order integration (New Order keeps reading `lib/garment-catalog.ts`'s static templates; this catalog's data is structured for future consumption — `getActiveGarmentTypes`, base price, linked measurement fields, linked add-ons, `calculateGarmentAmount` — but nothing calls it yet) — **this specific item was later closed the same day, see "New Order wired to Catalog" in Project status.**

Invoice/PDF generation is still not built.**

Run NewLook locally
on Windows

Build, copy, install and start — step by step

Your development PC → Customer ZIP
Customer main PC → App + local database
Shop browsers → Customer main PC

Prepared: 13 September 2026

Applies to: the current Build Customer Package.bat and its compiled Windows package. Example release: NewLook-Local-2026-09-12T05-35-15-030Z.zip.

Your current position: Docker and local Supabase have already been installed on your PC. The local schema was installed with 111 migrations and 46 public tables, and local admin login worked. Start with page 3 to test the copied package. Do not reinstall your existing schema.

How to use this guide

Complete one step, verify its expected result, then continue. Commands shown in grey boxes are for Windows PowerShell unless stated otherwise. Keep the application package and database in separate folders.

This guide contains no customer passwords, database keys or private login details. Record those separately in your private password manager.

The package was build-tested and browser-smoke-tested. Full customer-site installation, LAN rollout, catalog transfer and backup restoration are separate acceptance steps.

1. Understand what you are copying

LocationWhat belongs there
Your development PCOriginal repository, source code, npm dependencies and Build Customer Package.bat.
Customer application folderExtracted ZIP: compiled app, runtime dependencies, configuration, setup scripts and Start Server.bat.
Customer Supabase folder / Docker storageDatabase services, local secrets, database and uploaded-file storage. Preserve this when replacing the app.
Second shop PCA browser and network access to the main PC. It should use the same central database.

Included in the ZIP

  • app — compiled Next.js server and browser assets.
  • customer-server.mjs and Start Server.bat — daily launcher.
  • customer-config.json — database folder, public API URL, listening address and port.
  • setup — steps 01–05 and admin SQL.
  • scripts and supabase/migrations — one-time database installation tools.

Not included

Existing cloud orders, customers, catalog customizations and user accounts; installed Node.js, Git, Docker or WSL; downloaded Supabase images; your development environment files or original application TS/TSX source.

The app still contains compiled JavaScript, and the installer includes readable setup scripts and SQL. Someone with administrator access can inspect these. Packaging does not provide absolute code secrecy.

Internet and storage

Initial downloads need internet. Local features can run against the local services afterward; email, messaging and other external integrations still depend on their external services. Local storage is limited by disk space and system resources. It is not unlimited, and you are responsible for backups.

2. Build and test on your current PC

Step 1 — Generate the package

  1. Open E:\workspace\Tailor\tailorsaas\local-setup.
  2. Double-click Build Customer Package.bat. Run this on your development PC, where project dependencies are installed.
  3. Wait for the production build, type checking and ZIP creation to finish. Do not close the window during compression.
  4. Confirm PACKAGE READY and the success message. File Explorer opens the release folder.
  5. Use release\LATEST.txt to identify the newest ZIP. Copy the ZIP, not the original repository.

Expected: a timestamped folder and matching ZIP under E:\workspace\Tailor\tailorsaas\release. The first verified archive was approximately 7.08 MB; future builds may differ.

Step 2 — Extract a test copy

  1. Right-click the ZIP → Extract All. Choose a new test location, for example E:\TailorLocal\PackageTest.
  2. Open the extracted inner NewLook folder. Find Start Server.bat and customer-config.json.
  3. Check the configuration matches page 5. Your database folder is already E:\TailorLocal\supabase-local.
  4. Stop the old app terminal using Ctrl+C if it is already using port 3102. Leave Docker running.
  5. Double-click the packaged Start Server.bat and open http://localhost:3102.
  6. Sign in using your existing local admin account and its private password.
On your current PC, skip setup 02, 04 and 05 when the database and admin already exist. No customer-side build is needed. The repository's 06 Build App.bat belongs to the older developer-checkout workflow; it is not part of the customer ZIP.

Verify: login works, pages load, and data matches your local database. Missing cloud catalog items do not by themselves mean migrations failed; see page 8.

3. Fresh customer PC: prerequisites

Use this page only for a new Windows installation. A technician completes it once. Use supported Windows and hardware for Docker Desktop; check the official requirements before installation.

Step 1 — Install or verify WSL

  1. Save open work. Open PowerShell as administrator.
  2. Run the command below if WSL is not installed.
wsl --install

Restart Windows if requested. Finish any installation prompts, then open a new PowerShell and check:

wsl --version

Expected: WSL and kernel version information. WSL provides the Linux environment used by Docker on Windows. Microsoft WSL instructions.

Step 2 — Install Docker Desktop

  1. Download from the official Windows installation page. Choose x86_64 for an Intel/AMD PC; choose Arm only for an ARM-based PC.
  2. Follow the installer and use the WSL 2 / Linux containers backend. Restart if requested.
  3. Open Docker Desktop and wait until its engine is running.
docker version
docker compose version

Expected: docker version shows both Client and Server; Compose prints its version. A Client-only result with a connection error means the engine is not ready.

Step 3 — Install Node.js and Git

Install a supported Node.js LTS version, at least version 22 for these scripts, from nodejs.org. Install Git for Windows with Git Bash from git-scm.com. The setup expects Git Bash under C:\Program Files\Git\bin\bash.exe. Reopen PowerShell after installation.

node --version
git --version

No IDE is needed on the customer PC. Node runs the compiled app; Git is used for initial Supabase preparation.

4. Copy and configure the package

Step 1 — Choose the folders

Copy the ZIP to the main customer PC and extract it. Keep the full extracted folder structure. Do not run the BAT from inside the ZIP.

PurposeExample
Extracted applicationE:\TailorLocal\NewLookApp
Supabase services and local configurationE:\TailorLocal\supabase-local

If the PC has no E: drive, use an actual location such as C:\TailorLocal and change both settings below. For fresh setup, allow the preparation script to create the final supabase-local folder; do not pre-create an empty final folder.

Step 2 — Set the one-time setup directory

Open setup\settings.cmd in Notepad. Keep the syntax intact:

if not defined TAILOR_SUPABASE_DIR set "TAILOR_SUPABASE_DIR=E:\TailorLocal\supabase-local"

Step 3 — Set the daily launcher configuration

Open customer-config.json in Notepad. For a first test on the main PC, use:

{
  "supabaseDirectory": "E:\\TailorLocal\\supabase-local",
  "supabasePublicUrl": "http://localhost:8000",
  "bindAddress": "127.0.0.1",
  "port": 3102
}

JSON requires doubled backslashes in Windows paths and double quotes around text. Do not add comments or a comma after the final value. Both files must refer to the same Supabase directory.

Step 4 — Run the prerequisite check

Double-click setup\01 Check Requirements.bat. Confirm Node, Git, Docker and Compose are found. Fix any reported issue before continuing. This check finds the software; the database startup step verifies the services.

The two browser addresses have different purposes: localhost:3102 is NewLook; localhost:8000 opens local Supabase Studio for technician administration.

5. Install the local database once

Step 1 — Prepare Supabase

  1. Ensure internet is available and Docker Desktop is running.
  2. Double-click setup\02 Prepare Supabase.bat.
  3. Wait while it obtains the pinned Supabase configuration, generates local secrets on first creation and downloads the container images.
  4. Continue only after the message says Supabase is prepared.

The script uses Supabase self-hosted configuration tag self-hosted/v0.8.1. It preserves an existing .env file. Interrupted or example-secret configurations are blocked for technician review.

Step 2 — Start the database services

Double-click setup\03 Start Database.bat. It starts the containers and waits for health checks. First startup can take several minutes.

Expected: a successful return and the service list. If a service remains unhealthy, follow section 10; do not reset the database to fix a startup problem.

Step 3 — Install the application schema

  1. Only for a fresh database, double-click setup\04 Install Schema.bat.
  2. Wait for the success message. In the verified September 12 package, the expected result is 111 migrations, 46 public tables.
  3. Keep a record of the success message and package version.
Never use step 04 as an update command. It intentionally stops when public tables already exist. It does not copy cloud data or repair an existing installation. Do not delete existing tables to make the check pass.

Step 4 — Open local administration

Visit http://localhost:8000. If Studio asks for a dashboard username/password, the technician obtains DASHBOARD_USERNAME and DASHBOARD_PASSWORD privately from the local Supabase .env file. These are different from the NewLook application login.

Opening Studio confirms its page is reachable; it does not prove every service is healthy. Use the database startup result and health checks as well. Official self-hosted Supabase guide.

6. Create admin and start NewLook

Step 1 — Create the local authentication user

  1. Double-click setup\05 Create Admin.bat. It opens Studio and the admin SQL file in Notepad.
  2. In Studio, open Authentication → Users and select the action to create/add a user. Labels may vary with the Studio version.
  3. For this included bootstrap script, enter admin@tailor.test and choose a private password.
  4. Enable the option to confirm the user immediately. Do not send an invitation; local email delivery has not been configured by these scripts.

Step 2 — Link the user to the app

  1. Copy the entire contents of setup\create-local-admin.sql.
  2. In local Studio, open SQL Editor, create a new query, paste the SQL and run it.
  3. Confirm one result row: Local Admin and role-admin.

The SQL links this user to the seeded NewLook tenant and Main Shop. If no result appears, check the email, auth user and seeded tenant/shop. The script does not overwrite an existing profile. If you choose a different bootstrap email, a technician must update both email references in the SQL first.

Step 3 — Start the packaged app

  1. Return to the extracted package's top-level folder.
  2. Double-click Start Server.bat. Allow the database health checks and app startup to finish.
  3. Open your browser manually at http://localhost:3102.
  4. Sign in as admin@tailor.test using the private password you just set.

Expected: the app loads and authenticated pages are accessible. Leave the server window open. If port 3102 is already occupied, close the earlier app terminal before retrying.

Cloud logins are not automatically copied into this database. The dashboard password, database password and NewLook user password serve different purposes.

Why the catalog can be incomplete

Migrations install schema and the data explicitly included in their SQL. They do not automatically transfer catalog changes made in the cloud. Your earlier local comparison showed fewer garments than the cloud catalog. Catalog transfer was deliberately deferred.

  1. List required garments and prices separately for the men's and women's shops.
  2. Have the technician prepare and verify the catalog transfer or configure entries manually.
  3. Configure both shops and their local accounts; the bootstrap only creates a Main Shop admin.
  4. Repeat catalog and order checks before using real customer records.
Do not rerun all migrations or reset the local database just because garments are missing. Treat catalog transfer and shop/account setup as separate work.

8. Connect the second shop

Technician stage after the single-PC test passes. The current default package listens only on the main PC. A working same-PC login does not mean LAN deployment is ready.

  1. Choose one main server PC. Keep the app and central Supabase instance on it. Both shops must be able to reach this PC on the network.
  2. Reserve a stable LAN address. Ask the router/network administrator for a DHCP reservation. An address such as 192.168.1.50 below is only an example.
  3. Plan HTTPS and names. For operational use, configure a trusted local hostname/certificate and reverse proxy as appropriate. This is not automated by the current BAT files.
  4. Adjust the app configuration. Set bindAddress to 0.0.0.0. Set supabasePublicUrl to the API address that is reachable by browsers at both shops and by the server.
  5. Configure Supabase URLs. Align its public/auth URL settings with the chosen API URL, and SITE_URL/allowed redirects with the app URL. Apply changes through Compose and verify auth flows. Never place a secret/service key in a browser configuration.
  6. Allow only the required network access. The technician configures Windows Firewall for the trusted shop network. Keep database administration and raw database ports restricted; do not enable router internet forwarding for this local setup.
  7. Restart and verify. Test app login, API calls, saving and printing from each shop using its own local account.

Temporary LAN test example

With an approved private-network test configuration, the app may be opened at http://192.168.1.50:3102, with the public API at http://192.168.1.50:8000. Replace the example IP with the actual main PC address. This example is not a completed HTTPS deployment.

Do not use localhost on the second PC to reach the main PC. There, localhost means the second PC itself. Updating only the app address is insufficient if the browser's Supabase URL still points to localhost.

The main PC must stay awake while either shop is using the app. Windows-service installation and unattended restart have not been implemented in this package. Keep the server Windows session and launcher running during use.

9. Daily operation and updates

Start each day

  1. Turn on the main PC and sign in to Windows.
  2. Double-click the packaged Start Server.bat, or a shortcut pointing to it.
  3. Wait for startup, then open the app URL and sign in.
  4. Keep the launcher window and Docker running. Other shop users open the configured network URL.

Close for the day

  1. Ask both shops to finish and save their work.
  2. Press Ctrl+C in the app server window. This stops the app; the database containers normally remain running.
  3. If shutting down the PC, allow services to stop cleanly. Avoid forced power-off.

Create a desktop shortcut

Right-click Start Server.bat and choose the Windows option to create/send a shortcut to the desktop. Move the shortcut only; keep the BAT inside its package folder.

Update the application later

  1. Build a new ZIP on the development PC and record its version.
  2. Before changing the customer installation, arrange and verify a database/storage backup.
  3. Check release notes for database changes. The included schema installer cannot upgrade an existing database. A technician must supply any required incremental migration procedure.
  4. Stop the old app and extract the new package into a separate versioned folder.
  5. Copy the reviewed customer configuration to the new folder and point it at the same existing Supabase directory.
  6. Start and verify the new app. Keep the previous package for investigation or a compatible rollback. A database change may prevent simply returning to the old app.
  7. Update the desktop shortcut after acceptance.
An app ZIP is not a data backup. Keep Supabase data/configuration separate from versioned application folders. Do not rerun fresh-install steps as part of a routine app update.

10. Troubleshooting reference

SymptomWhat to do
node or git not recognizedInstall the required software, reopen the terminal, then rerun 01. Node must be version 22 or newer.
Docker engine connection errorOpen Docker Desktop, wait for the Linux engine, then check docker version shows a Server section. Complete any pending WSL restart.
Target folder exists without ComposeStep 02 protects existing folders. Inspect that folder; use a new destination and update both configuration files. Do not delete unknown contents.
Secret generation interrupted / example secretStop setup and have a technician inspect the .env and marker. Do not remove the marker or regenerate live keys blindly.
Storage or realtime unhealthyCheck status and recent logs with the commands below. Studio opening does not prove these services are healthy.
Database already has public tablesStep 04 is intentionally blocked. If installation already succeeded, skip it. Otherwise inspect the existing schema before any repair.
Port 3102 already in useClose the previous NewLook server terminal. Do not start both the developer and packaged servers on the same port.
Invalid credentialsUse a local auth account, not an assumed cloud login. Check confirmation and the linked public profile in local Studio.
Main PC works, second shop failsCheck LAN address, bindAddress, firewall, reachable public API URL and trusted HTTPS configuration.

Read-only diagnostics in PowerShell

Set-Location 'E:\TailorLocal\supabase-local'
docker --context desktop-linux compose ps
docker --context desktop-linux compose logs --tail 80 storage realtime

Run Compose from the Supabase directory to avoid relative COMPOSE_FILE path errors. Review logs for private values before sharing them. If a command is not found, reopen PowerShell after installation.

Never use a database reset, Docker factory reset, volume removal or compose down -v as routine troubleshooting. These can remove locally stored data.

11. Backups and handover record

Before real customer use

Backup automation is not included yet. Assign a technician to implement and test recovery for this exact installation. Saving only the application ZIP or copying a running database folder is not sufficient.

  1. Identify database persistence, uploaded-file storage and Docker named volumes from the installed Compose configuration.
  2. Create a consistent database backup using a suitable database backup procedure; preserve required roles/auth data and any encryption material needed to restore.
  3. Back up uploaded files separately where applicable, plus the local .env, Compose configuration and customer-config.json. Protect these backups because they may contain private records and credentials.
  4. Keep a copy away from the main PC and record the backup date.
  5. Restore to a separate test instance and verify login, sample orders, balances and uploaded files. Record the restoration result before relying on the backup.
